# TechPath host integration

## SQL execution + structured grading (v0.4)

The local connector serves authenticated `/api/sql/status` and `/api/sql/run` routes with the same exact-origin/Host gates and process token as the tutor. A native Windows PowerShell/System.Data.SqlClient worker talks to `localhost\SQLEXPRESS` with Windows authentication. Provisioning creates an owned `TechPathLab_<random>` database identified by an extended property, seeds the authored SupportLab dataset once, and refuses an existing database with a different identity. TRUSTWORTHY and database chaining are disabled. Learner batches use a database user without login via `EXECUTE AS USER ... WITH NO REVERT` on a fresh nonpooled connection. This user has SELECT, VIEW DEFINITION, EXECUTE, CREATE PROCEDURE and schema ALTER within the disposable lab; it is not given server/admin/cross-database access. No learner SQL is executed with the bootstrap connection's original identity. `GO` is split outside strings/comments; a standalone `USE SupportLab` is redirected to this database. Limits: 20 batches, 10 result sets, 500 rows per set, 100 columns, bounded cell/output size, 10-second command timeout, 30-second soft total limit and 45-second worker deadline. Cancel kills only the owned worker and closes its connection.

Node retains bounded run records bound to browser identity, lesson and SHA-256 of submitted code. A grade request carries a run id; the connector looks up actual results and ignores client-supplied execution metadata. Changed/expired results are not accepted as current. Query errors and truncation prevent a pass. Runs do not call an AI model. Procedures persist in the per-machine lab; browser backup does not transport database objects.

`purpose:grade` loads the trusted authored lesson/task/checklist and reference on the server and requests `turn/start.outputSchema`. All criteria must appear once with a valid status. The final JSON is parsed and validated, never detected by keyword matching in chat text. Non-met/unknown criteria downgrade the verdict; optimization comments alone do not fail a correct answer. Malformed, missing, cancelled and failed responses never mark completion. Grading output is rendered as safe text/HTML generated by the app; raw JSON streaming is suppressed. Normal tutor follow-ups omit the output schema and never change progression. The schema also requires an `answers` array when the learner asked a question; each item has a short `topic` and `text`, is validated (non-empty and bounded), and is stored with the attempt, JSON backup and Markdown export. An empty `answers` array is rejected for a non-empty question rather than silently dropping the explanation.

The browser freezes each submission before asking AI, records the result against that lesson and snapshot, and checks for edits before advancing. Only a valid `pass` on the unchanged visible lesson advances automatically. Skip saves the draft as `skipped`, never `ai_pass`, and the library has a skipped filter. Past manual assessments are preserved and labelled as history. Backup/import and Markdown exports retain grading notes, explanations and skipped attempts. No end-to-end model-grading request was made as part of this change; build parsing and real lab provisioning do not establish that a model verdict is correct.

## Direct tutor (v0.3, updated v0.4)

The standalone Site now opens a persistent tutor side panel. A review click snapshots the actual task, code, output/error, notes and question using `packet()`, then sends them once to the local connector. Follow-up questions stay in the same lesson conversation and include the latest draft when still viewing that lesson. Empty input is rejected; no typing or page-load event starts inference. Plain text rendering prevents code/HTML from executing in replies. Stop aborts the HTTP stream and requests `turn/interrupt`; errors never auto-replay inference.

Run `Start-TechPath.cmd` on each Windows device. Node serves the app and `/api/tutor/*` only on 127.0.0.1:4173. It can launch `codex app-server --stdio` on demand and requires `account/read` to report a ChatGPT account before Codex generation, or use 9Router on 127.0.0.1:20128 for Antigravity (Gemini, Claude, GPT-OSS). Codex uses model `gpt-6.1-sol`, effort `low`, provider `openai`, with no automatic model/provider fallback. Antigravity uses the model selected from the active 9Router catalog; the app does not silently switch models on error. TechPath does not extract or transmit authentication tokens. API key environment variables are removed from the Codex child environment and API-key-only accounts are rejected. 9Router may require `TECHPATH_9ROUTER_API_KEY` if its gateway is configured with a key. Both paths use existing plan/provider limits; this is not unlimited free inference.

The hosted Site may connect to that local endpoint only after browser local-network policy allows it. Exact allowed Origin and Host checks, a fresh random per-process request token, JSON-only POSTs and bounded body size prevent arbitrary websites from invoking it. The token is held only in browser/process memory. No wildcard CORS or public listener is used. If the browser prevents hosted-to-loopback fetch, use the local UI and transfer progress through JSON. The plugin sandbox's restrictive CSP may also prevent direct local connections; the standalone Site/local UI is the primary path.

Each local review request starts an ephemeral Codex thread, or one 9Router chat completion. No Codex thread mapping is persisted; `.techpath-local/sessions.json` is legacy data from the earlier persistent-thread transport. Shared memory is the bounded visible history sent by the browser plus the current lesson snapshot. This never resumes or modifies the chat used to build the app. A learner-approved profile and tutoring instructions provide personalization; that is not a copy of the whole original conversation. Visible tutor history is included in JSON backup and restored by import, but it is not a copy of the provider's hidden thread.

Tutor prompts prohibit tools and the thread uses a read-only sandbox; server-initiated approval/tool requests are rejected. `turn/start` sends `{type:"readOnly"}` without the retired `readOnly.access` field. A restricted read allowlist would require a supported permission profile rather than that legacy field; the app does not claim a folder-only read allowlist. The tutor is not a SQL executor; SQL execution is the separate local lab described above. Never report a query as actually run by the tutor. The connector does not directly read SSMS.

Follow-up messages send the latest six visible turns (bounded to 6,000 characters total) plus the current lesson snapshot as a separate `BÀI LÀM THAM KHẢO` block and the new question under `CÂU HỎI LẦN NÀY`. The snapshot is resent each follow-up so the model can answer against the actual code; duplicate conversation history is avoided by sending only the bounded recent turns, not the whole page. On reload the same rule applies. This reduces duplicate input without claiming a particular percentage reduction in plan usage. Sign in with ChatGPT plan usage still counts toward existing Codex / ChatGPT work limits; switching the sign-in transport does not grant a separate chat allowance.

Verification: `npm run check:all` covers data contracts, grading parsing/rendering and MCP routes without calling a model or SQL Server. A live model review is still required to confirm provider behavior, latency and that a model follows the `answers` schema; deployment success alone is not proof of model inference.

### Missing-rollout recovery (v0.3.2, historical)

The persistent-thread mapping described here is no longer used by the local connector; v0.4 starts ephemeral threads and sends bounded history each turn. The recovery behavior is kept as a record of the earlier transport. Thread allocation alone does not establish that a durable rollout exists. New mappings were persisted only after a completed answer. A legacy mapping that failed `thread/resume` with the specific `no rollout found for thread id` error was removed and replaced before any model turn started. Other resume/start/auth/quota failures were surfaced without retrying inference. The browser sends a bounded `contextPrompt` alongside follow-ups; the earlier connector injected it only for a newly created conversation, so recovery could not send an out-of-context follow-up. Completed inference was reported as completed even if saving the session mapping failed, with a separate persistence warning. Browser drafts and visible history were preserved.

## Architecture

Sites private access gate -> Worker `/mcp` -> read-only lesson/profile tools + MCP Apps UI resource. UI runs the same curriculum and local learning flow. A deliberate button click previews and sends a message through the MCP Apps host bridge. The host's current conversation supplies the assistant and selected model; the app never selects a replacement model or creates a paid API request.

The UI resource is self-contained (inline CSS/JS, no external fonts, no nested iframe) with an empty CSP resource/connect allowlist. It handshakes using `ui/initialize`, handles `ui/notifications/tool-result`, and sends `ui/message`. The optional official `window.openai.sendFollowUpMessage` compatibility API is used only when present and the standard bridge has not initialized. An uncertain send is never automatically replayed.

## Data and access

- Sites verifies caller access before forwarding `/mcp`; audience remains private.
- MCP tool `get_techpath_profile` returns only learner-approved course preferences, not private contact details or chat logs.
- `get_techpath_lesson` excludes reference solutions unless explicitly requested with `include_solution=true`.
- Draft code/errors are supplied only on the learner's send click, after a visible preview. No SSMS access is claimed.
- No raw conversation-reading API, authentication token extraction, browser UI automation relay or new chat creation is used.
- The app does not set, query or claim to verify the host's selected model. Keep GPT-6.1 Sol / Light selected in the host UI.
- Browser-local persistence and optional host widget-state are separate from model context. The JSON backup remains the portable source for progress between browser environments.

## Native entrypoint

`open_techpath` metadata declares `_meta.ui.resourceUri` and the thread entrypoint using `openai/ui`. `resources/read` returns `text/html;profile=mcp-app`. Legacy output-template metadata is included for compatible hosts. Tools remain usable when UI rendering is unavailable.

## Verification boundary

`checks-mcp.mjs` verifies RPC contracts, explicit-only sends, no implicit solution disclosure, message-source validation and Worker HTTP routes. `checks-tutor.mjs` verifies grading schema/parsing and explanation handling without a model call. A successful build/deployment is not proof that a specific ChatGPT/Codex client loads the UI or sends a live message. Verify that separately after the generated plugin is installed and visible to the current chat. If connection needs user approval, report it rather than claiming end-to-end completion.
